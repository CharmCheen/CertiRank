# CertiRank 两周执行计划

周期：2026-10-15—2026-10-28，共 14 个自然日（Asia/Shanghai）  
版本：v0.1  
性质：探索性机制验证与冻结后的查询留出检查  
配套文档：[研究总纲](CertiRank_研究总纲_v0.1.md)

> 两周结束时应得到一个可以执行的研究判断：继续完整机制、保留预算分配、保留简单规则、仅保留测量结论，或停止当前路线。目标是取得支持该判断的证据与最小原型。

## 1. 目的与范围

围绕三个问题开展工作：

1. 相同请求的比较变化，在当前固定工作负载上是否导致值得优化的 Top-K 集合分歧？
2. 当前执行轨迹中的信息，能否帮助挑选比置信度或简单拓扑规则更有价值的复核对象？
3. 复核改变比较决策后，增量执行相对于从头重放并合法复用比较结果，能节省多少实际成本？

两周内交付：可重放的固定算子、隔离信息权限的实验框架、一个冻结的复核策略、与基线的成本和结果对照、明确的后续决策。

首阶段不安排通用符号执行引擎、多翻转最小证书或完整物理优化器。计划遵循依赖顺序；某个关键阶段未通过时，后续日期用于诊断和结论整理。

## 3. 固定的最小实验协议

### 3.1 主变量与比较对象

| 项目 | 约定 |
| --- | --- |
| 候选集合与查询 | 按预定检索或数据集规则生成；不能按实测不稳定性筛选测试查询 |
| 主任务 | 无序 Top-3 集合 |
| 主算子 | 固定叶序、固定提取规则的 Tournament；先验证 Top-1 更新，再支持 Top-3 |
| 对照算子 | 当前已有且可以重放的 Top-K 实现 |
| 主实验模型与 Prompt | 固定一个已批准配置，继承可复用协议 |
| 呈现顺序 | 按固定文档 ID 顺序呈现，主实验不交换 A/B |
| 首要预算 | 额外 +40%；次要预算 +20% |
| 预算基数 | 每个 query/run 的无复核执行调用数 L0，预算 B=floor(b×L0) |
| 成本边界 | 显式复核与新分支比较均消耗 B；失败与重试另记物理成本 |
| 投票规则 | 已有一次回答，再追加两次形成三次多数票；每个请求最多进入一轮复核 |
| 同执行复用 | 相同请求的已获得结果可复用，所有方法遵守相同规则；显式复核必须获取新响应 |
| 跨执行缓存 | 禁用；独立执行使用独立响应池 |

投票需要两次额外调用，+20% 预算在小 N 上可能只支持一两条边。预算不能通过四舍五入增加；需同时报告 B 和完成的复核次数。

若一次更新触发的新分支不能在剩余预算内完成，保留最后一个完整有效输出，记录该次修复为 aborted，以及已经消耗的调用。所有方法共用该规则，不能向沙盒免费读取结果来“补齐”。

### 3.2 数据分组与调用规模

优先完成或复用原有 3-query Gate 2，作为现象检查。新策略实验建议采用以下最低设计：

| 数据块 | 目的 | 建议配置 | 完整采集的调用上限，不含重试 |
| --- | --- | --- | --- |
| 开发集 | 设计、调试、选择策略 | 6 个 query-group，N=8，12 次同序回答/对 | 6×28×12=2,016 |
| 查询留出集 | 冻结后评估 | 12 个未参与开发的 query-group，N=8，12 次同序回答/对 | 12×28×12=4,032 |
| N 扩展开发块，可选 | 检查小 N 特例 | 4 个开发查询，N=16，12 次同序回答/对 | 4×120×12=5,760 |

核心开发与留出共 6,048 次比较；加入可选 N 扩展后为 11,808 次。历史数据是否能减少新调用，由请求配置、时间窗口和重复槽位是否兼容决定，不能直接相减。

以上为建议数据规模，不构成付费授权。先根据每请求实测输入/输出 token 与当前服务计价计算金额，再在已有明确授权范围内运行；新授权应包含逻辑调用、物理尝试、金额与截止时间上限。预算不足时，在查看留出结果之前调整规模并记录协议版本，必要时把结论标为不充分，不降低验证标准。

分组单位是独立查询及其相关变体；同一基础查询的 paraphrase 或候选集变体必须放在同一组。若独立组不足，应如实报告有效组数，不用改写查询凑足样本。

### 3.3 响应池如何模拟独立完整执行

每对的 12 次回答预先分成 4 个互不重叠的槽位组，每组 3 个回答。每组代表一个完整算法执行：首次比较使用槽位 1，显式复核使用槽位 2、3。修复路径请求新比较时，使用该请求在本组中的槽位 1，按新调用计费。

这是有限响应表上的受控重放设计。采用同一响应组比较不同策略，可减少比较方差；不同完整执行必须使用不同组。表的第 j 列只是实验索引，不能假设所有调用天然共享一个一致的“世界”。

在线模块只能通过 `observe`/`probe` 接口访问已付费信息。评估器可看到全表，用于事后分析和理想上界。原始 provider 缓存、实验日志复用、策略显式复核分别记录，防止混淆。

按随机或交错顺序采集各查询/比较/重复槽位，记录时间戳和服务版本信息。若时间漂移或依赖显著，不把这些组直接宣称为严格独立样本；在真实按需运行中补查。12 次重复属于先导配置，无法支撑很低违约率的统计认证。

### 3.4 基线与消融

| 名称 | 做法 | 作用 |
| --- | --- | --- |
| Base | 无复核的固定算子 | 测量初始分歧与调用基数 |
| Random | 从已观测、未复核比较中随机选取 | 排除追加调用本身的收益 |
| Confidence | 预先定义的低 logprob margin 优先 | 检查结构信息是否超越模型信号 |
| SimpleTopology | 按到最终输出的依赖距离优先，稳定 ID 打破平局 | 防止复杂方案只赢弱基线 |
| Proposed | 冻结的结构/置信度/恢复成本策略 | 主方法 |
| Vote3 | 实际路径上的比较均三次投票 | 较高成本参考，按实际路径计费 |
| OracleImpact | 利用完整表事后知道翻转影响 | 不可部署理想对照，不进入公平排名 |

若接口没有 token logprobs，记为 unavailable，不以 LLM 自报“置信度”冒充。主张相应收缩为优于可用基线；未经授权不为获取该信号更换服务。结构与置信度的消融只在信号可用时执行。

复核策略的比较共用同一修复器。修复器的比较共用同一复核顺序，分别运行：全新执行、从头重放并合法复用请求结果、增量执行。区分请求缓存和控制流增量带来的收益。

## 5. 分阶段任务：目的、思路、预期结果与处理

### P0｜10/15：核对最新状态，冻结最小语义

**目的**：避免重做已完成实验，以及把历史失败状态或未验证猜测带入后续实现。

**执行思路**：

1. 只读核对仓库状态和最新 artifacts，记录 source revision、配置 hash、调用成功/失败数量与是否已有传播分析。
2. 若 Gate 2 已完整完成，先分析已有结果。若只有部分数据，确认 resume 的行为后补缺。若仍阻塞，保留阻塞证据并推进离线模块。
3. 定义 Top-K 集合语义、请求键、调用实例、输入顺序、同执行复用和跨执行隔离。
4. 写出开发/留出分组、预算与主要指标；为新增付费运行准备完整预算清单。

**预期结果**：可以明确区分已有、缺失、失败、不可复用的数据；任何执行者都能复现同一协议。

**交付与通过条件**：`current_state.md` 和 `protocol.yaml`；已完成数据有可定位来源；未提交修改没有被覆盖；所有成本上限可计算。

**后续处理**：状态不明时优先定位一次具体运行，不重启全量实验。接口或额度阻塞不阻止 P1；没有真实回答时，P2 结论标记 pending。

### P1｜10/16：用小例子建立可信执行基础

**目的**：先证明记录、重放和局部恢复实现正确，澄清“未知”和“无害”。

**执行思路**：

1. 构造四元素反例 A>B、C>D、A>C，分别设置 A>D 与 D>A，验证翻转 C>D 后输出不同。
2. 构造严格全序、非传递三元环、同一请求重复变化的例子。
3. 实现固定 Tournament 的 Top-1 和固定规则 Top-3；明确胜者提取、节点失效与重复请求复用行为。
4. 对 N=4 的确定二元反对称比较表，可穷举全部 2^6=64 张表，检查重放和单次更新；N=6/8 用可重复随机实例补查。
5. 在相同后续响应下，对比增量执行与从头重放。提前触发预算耗尽和新分支，验证保留最后完整输出的行为。

**预期结果**：原始重放完全一致；增量与从头重放结果一致；未观测比较不会被悄悄推断成传递关系。

**交付与通过条件**：最小 fixtures 和相关正确性测试全部通过；新比较访问有计费记录；证明不了的剪枝返回 unresolved。该有限穷举仅覆盖相应输入模型，不替代一般性证明。

**后续处理**：正确性未通过时停止性能优化。若通用状态快照成本过高，改为算子特定事件与检查点；先只保留一个主算子。

### P2｜10/17—10/18：确认真实传播现象与收益上限

**目的**：回答当前配置是否值得做可靠性优化，并区分真实关键性与在线可识别性。

**执行思路**：

1. 优先使用更新后的 Gate 2 数据，检查相同请求 hash 的翻转、Top-3 Exact Match 分歧、Jaccard 距离及标签质量。
2. 固定物理算法和输入，先观察调用变化；呈现扰动和计划变化另表报告。
3. 在完整表可用的小规模实例上逐条翻转原始比较，并用固定表补全反事实路径。记录输出变化与未观测请求数量。
4. 对同一轨迹计算保守 unknown 集合，并与事后真正有影响的边比较，观察信息缺口。
5. 合成噪声只用于验证因果机制和工具；真实 LLM 数据单独列出。

**预期结果**：得到逐查询的传播与吸收图景，明确是否存在结果分歧，关键性是否能被在线信号捕捉。

**交付与通过条件**：`phenomenon_report.md` 至少包含逐查询比较变化、集合分歧、条件关键性与新比较分布。不给 unknown 强行填零。

**后续处理**：若完整执行平均 D_EM 很低（例如低于 0.10），先记录改善空间有限；仅凭 3 个查询不能宣布方向失败。可按预定规则增加开发查询，不能按不稳定程度筛选。若没有真实集合分歧，保留负结果，暂不采集整个留出集。

### P3｜10/19—10/20：实现一个可在线运行的复核策略

**目的**：检验执行结构是否提供额外选择信息，同时控制实现复杂度。

**执行思路**：

1. 采集或复用开发集，所有候选策略只能通过受控接口观察数据。
2. 优先完成 Random、Confidence（可用时）、SimpleTopology，测出真正需要超过的基线。
3. Proposed 只使用少量可解释特征，例如到输出的依赖距离、受影响候选数量的保守估计、已知恢复路径长度和置信度。
4. 预先限制开发规模：至多 3 个策略版本、每版少量参数；记录每次变化理由。先采用简单组合或排序，不训练复杂模型。
5. 对照 OracleImpact 分析：若事后最优选择都无明显收益，及时停止选择策略的复杂化。

**预期结果**：得到可复现、无全表泄漏的复核顺序；知道收益来自结构、置信度、追加调用还是缓存。

**交付与通过条件**：`policy_spec.md` 写出特征、公式、平局规则、每步是否重新排序及缺失信号处理；开发结果包含所有尝试，保留失败版本记录。

**后续处理**：若复杂方法与简单拓扑相当，选简单规则作为最终方法。若只在使用完整表时有效，标记在线可观测性未解决，不进入留出集调参循环。

### P4｜10/21：冻结方法，决定是否投入第二周

**目的**：让第二周真正检验第一周的判断，避免持续修改标准。

**执行思路**：

1. 固定唯一 Proposed 与一个主要 comparator；comparator 从开发集选择最强的可部署简单基线，选择规则提前写清。
2. 冻结 source revision、数据组、预算、Prompt、策略、指标和所有分析参数。
3. 预先指定增量机制的主要成本指标：模型调用、CPU 重算或延迟中的一项，并保留其余指标。
4. 将未使用的查询组封存；已看过结果的查询转为开发数据。

**预期结果**：形成一个能被否定的固定版本，以及进入第二周的理由。

**交付与通过条件**：`freeze_manifest.json`、`week1_decision.md`。前者可追踪所有实现与配置；后者明确 proceed、simplify、hold 或 stop。

**后续处理**：若仍有正确性错误或信息泄漏，不开启正式留出评价。若开发集效果弱且置信区间很宽，只可开展有上限的样本补充，不能承诺完整系统。

### P5｜10/22—10/24：留出查询上比较完整算法

**目的**：检查机制在新查询上的效果，并衡量不确定性。

**执行思路**：

1. 用冻结方法在查询留出集运行全部基线；同一组响应支持配对方法比较，不同完整执行使用不重叠槽位。
2. 对每查询 4 个完整执行计算 6 个执行对的分歧，然后先在查询内汇总，再跨查询取平均。
3. Bootstrap 以独立 query-group 为单位；6 个执行对不被当作 6 个独立查询。小样本下同时报告逐查询值和区间。
4. 使用独立标签计算质量。单相关文档查询报告 Recall@3；只有完整有序输出时才报告 nDCG。
5. 记录实际调用/token、预算耗尽、未完成修复、CPU 分析、缓存复用与尾部成本。绘制成本—分歧曲线，不能只给预算标签。

**预期结果**：能够判断是否超越预先确定的强基线，改善是否集中于个别查询，质量是否出现损失。

**交付与通过条件**：`heldout_results.csv`、逐查询图与 query-group bootstrap 区间；所有失败均有明确状态，没有静默删除。

**后续处理**：测试结果不理想时先记录。新的改动进入下一轮开发，当前留出集不能再被称为未见测试集。若标签或有效查询数不足，只给一致性探索结论。

### P6｜10/25—10/26：真实按需执行与成本归因

**目的**：确认离线受控表上的结果可以落实到实际调用行为，检查批处理与串行依赖的影响。

**执行思路**：

1. 预先选择 2—3 个查询做真实按需 smoke，覆盖不同轨迹长度；选择规则在查看该轮结果前确定，不能专挑提升最大的查询。
2. 在批准预算内交错运行 Base、主要 comparator、Proposed，记录实际请求顺序、失败与耗时。该小规模 smoke 只验证行为可迁移性，不承担显著性结论。
3. 固定复核顺序，对比增量执行与从头重放加合法缓存，确保后续请求使用相同响应时结果一致。
4. 测量串行依赖轮数、batch 大小和端到端延迟；若调用减少但延迟增加，解释来源。
5. 有剩余预算时，在开发查询上做 N=16 的诊断扩展；N=32/64 的在线扩展留给下一阶段，或明确标为额外探索。

**预期结果**：确认日志、预算和真实服务调用一致；区分省调用、省 CPU 与省延迟三种收益。

**交付与通过条件**：`live_validation.md` 与修复消融表。真实接口行为与离线模拟不一致的地方必须列出。

**后续处理**：若缺少付费授权或接口不可用，完成离线正确性与成本归因，把 live 验证列为真实阻塞。若缓存重放已经取得同样效果，保留简单实现。

### P7｜10/27—10/28：形成研究裁决与下一阶段输入

**目的**：依据证据决定投入范围，保留可复用成果与负结果。

**执行思路**：

1. 汇总 H0—H3 的支持证据、反证、未验证部分和适用范围。
2. 将机制、实现、资源与统计不确定性分开解释。
3. 选择一个后续分支，并明确下一阶段新增问题、主指标与停止条件。
4. 清点 artifacts、版本、实际支出与复现命令，确保其他执行者能接续。

**预期结果**：得到明确、可追溯的研究决策，而非只有一组漂亮平均数。

**交付与完成条件**：`two_week_report.md` 和一页 `decision.md`；报告包含全部基线、逐查询结果、预算台账、局限与下一步。

## 6. 决策标准与结果解释

以下阈值用于项目投入裁决，在 10/21 前冻结；它们不代表理论必要条件。

### 6.1 必须先通过的实现 Gate

- 固定响应条件下，原始重放结果 100% 一致。
- 已执行的合成穷举与随机测试中，增量执行与从头重放结果一致。
- 在线策略无未计费的响应表访问；每次失败、重试和预算耗尽有记录。
- 开发与留出 query-group 隔离，方法冻结可核对。

### 6.2 支持继续投入的研究信号

主比较为 +40% 预算下 Proposed 对冻结的最强简单基线。相同预算上限不保证实际消耗完全相同，因此同时报告实际成本与完整曲线；不通过无意义调用补齐预算。

- 平均 D_EM 绝对降低至少 0.05，同时相对降低至少 25%。
- 独立标签质量平均下降不超过 0.02；如果区间不能排除更大损失，结论标为质量尚未证实。
- 改善出现于多个独立查询；报告各查询方向，不能由一个异常查询主导。
- 实际成本被完整计入；+20% 的结果作为预算敏感性检查，不替换主比较。

相对降低按 (D_baseline−D_proposed)/D_baseline 计算；若基线分歧为零，该项不定义，并记录已无可观测改善空间。

四次完整执行与少量查询会产生较宽区间。满足点估计门槛仅支持探索性推进；若配对区间仍跨零，下一阶段首先扩大独立查询与重复数。N=8 的结果只能说明小候选集上的机制，不能支持大规模效率结论。

增量执行单独判断：在预先指定的主要成本上，相对从头重放加合法缓存减少至少 25%，且保持输出一致。若仅 CPU 成本改善，结论也限定在 CPU。

### 6.3 各种结果如何处理

| 结果 | 裁决 | 下一阶段 |
| --- | --- | --- |
| 策略和增量执行均有稳定收益，质量可接受 | Proceed | 扩大 N/K、查询与服务配置，开始真实引擎集成 |
| 策略有效，增量无额外收益 | Narrow | 保留预算分配，采用简单缓存重放 |
| 简单拓扑胜出或与复杂策略相当 | Simplify | 以简单策略为核心，研究适用边界 |
| 理想上界强，在线方法弱 | Hold | 最多再安排一个短周期研究可观测信号；没有改善则停止复杂选择路线 |
| 理想上界也弱，或基准本就高度稳定 | Stop current setup | 保存负结果；扩展任务需要独立动机与新协议 |
| 一致性提高，质量下降超过容忍范围 | Fail quality gate | 不启动全面实现；检查决策目标和复核规则 |
| 只有个别查询有效或区间很宽 | Exploratory only | 先补独立查询，暂不宣称泛化 |
| 缺响应、缺标签、缺预算或服务异常 | Inconclusive | 明确阻塞与所需最小补充，不作正负科学判断 |

## 9. 两周报告模板

最终报告依次回答：

1. **目的与冻结协议**：实际检验了哪个假设，哪些条件固定。
2. **数据与执行状态**：有效独立查询数、候选规模、重复数、失败与实际成本。
3. **现象**：比较变化如何传播，哪些情形被吸收，unknown 有多少。
4. **方法效果**：成本、分歧、质量的联合结果，与全部基线比较。
5. **机制归因**：结构、置信度、请求缓存、增量执行各贡献多少。
6. **证据等级**：探索信号、冻结后留出结果、未泛化部分与被否定假设。
7. **决策**：选定一个后续分支，列出下一阶段最小新增实验与停止条件。

一页 `decision.md` 应让读者只看这一页就知道：完成了什么、结论由什么支撑、当前保留哪一项技术主张、还有什么真实阻塞。
