## 1. 问题

LOTUS Gate 2 已证实：LLM 成对比较算子是非确定性的——同一请求五次独立发送，
约三分之一 (29/84) 的 pair 出现过不同判定，且这种算子层噪声会传播到查询答案
（每条 query 的 5 次重复产生了 2–3 个不同的有序 Top-3，有序完全一致率仅 30%）。
同时，算子不稳定与答案影响严重错位：37 个高影响对中仅 14 个翻转过，
23/37 ≈ 62% 的高影响对在五次重复中从未翻转（详见审计报告 §4 的单位说明）。
"盯住抖动的地方复核"既漏掉真正要害、又浪费在无效位置上。

CertiRank 要回答的问题是：**在 Tournament 式的排序执行中，能否用在线可获得的
信息（执行轨迹上的结构信号）指导选择性复核，以显著更少的额外调用换取答案
稳定性的可证明改善？**——并且答案必须能在真实系统上成立。

## 2. 与 LOTUS 实验的关系（边界声明）

- CertiRank 是**独立的小型研究原型**，不搬运 LOTUS 仓库代码。
- LOTUS 提供两样东西：冻结的 Pair Response Pool（420 条真实响应，见
  `data/external/lotus_gate2/`，manifest 记录哈希与来源）和已验证的算子语义
  （naive sort 的投票/平票规则，已在 `certirank.operators` 独立实现并通过
  合成用例与 Gate 2 数据的双重检验）。
- 排序算法（旧）、真实 LLM 响应（旧）、CertiRank 的执行与复核机制（新）
  三者严格分离。是否实现完整 Incremental Repair，待第一周结果决定。

## 3. 信息边界（本研究的效度核心）

| 层 | 内容 | 允许用途 |
|---|---|---|
| 完整响应表 | 84 slot × 5 响应的离线固定表 | 离线评价、反事实上界、OracleImpact 事后分析 |
| 在线执行轨迹 | Tournament 实际执行路径上读到的比较事件 | 复核策略的唯一在线信息来源 |
| 新分支请求 | 执行路径需要但表中没有的比较 | 必须实际调用，计入预算 |

把完整响应表交给在线策略，后续即使观察到显著改善也无法证明真实系统可实现——
这是 Gate 2C 讨论冻结的边界，所有 P2/P3 实现必须遵守（规范见
`configs/protocol.yaml` 的 `information_boundary`）。

## 4. 方法骨架

1. **执行器**（P2）：固定规则的 Tournament（先合成比较表验证正确性，再用
   Gate 2 兼容响应离线执行），记录比较事件轨迹，输出 Top-1/Top-3。
2. **策略**（P3）：Random、SimpleTopology、初步结构感知三档；置信度信号仅在
   原始数据支持时启用。比较在线可获得信息与事后 OracleImpact 的差距。
3. **判定**：若出现可信的收益信号 → 冻结协议，进入留出查询验证；
   若无 → 诚实记录负结果，再决定是否继续。

## 5. 成功条件（第一周收敛版）

在固定且经过验证的 Pair 响应数据上：
- [x] 正确执行 Tournament、记录控制流（P2 交付后勾选）；
- [x] 数据基础：Gate 2 原始 artifacts 恢复、契约建立、核心统计一条命令可复现
      （P0 已完成，22/22 项审计通过）；
- [ ] 分析比较变化对结果的影响（单边翻转、新分支比较、敏感度）；
- [ ] 初步判断在线结构信息能否指导复核。

## 6. 当前已知风险与限制

- 外部数据来自重定向端点（Paratera / DeepSeek-V4.1-Flash），翻转率不可与
  Gate 1 官方端点数据直接比较；
- 3 query × 5 重复只是 pilot 规模；正式统计验证需补充独立查询与重复
  （两周计划的 P1 之后持续进行）；
- SciFact 每 query 恰一篇相关文档且稳定在 rank 1，nDCG@3 对本设计中的
  不稳定性不敏感——稳定性结论必须依赖 Top-3 集合/有序指标。
